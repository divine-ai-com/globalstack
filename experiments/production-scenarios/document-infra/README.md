# Document deployment modules

These modules cover document storage and event routing. A successful Bicep build or ARM deployment does not show that an uploaded document completed processing. For the current evidence and remaining gates, see [the production-scenario status](../STATUS.md). The dated pilot descriptions below retain the outcome at each capture, including failures later repaired.

`document-ingress-app.bicep` declares the authenticated document API as a single-replica Container App with a user-assigned identity, a pinned image reference supplied by the runner, managed registry access and HTTPS-only ingress. Runtime settings are supplied from deployment outputs and the operator-owned API registration. Its reviewed compiled ARM fixture is checked in CI. This is an infrastructure artifact, not yet a live Azure or GlobalStack ingress result. Native Container App managed-identity transport and a paired application run remain required.

`document-data.bicep` creates the document account and four private containers. It enables Blob versioning and a seven-day soft-delete window. The account name, location, and run identifier come from the experiment manifest. The account is distinct from the Functions host-storage account in `worker-host.bicep`. Scoped Blob Data Contributor assignments allow the pilot identity to upload test files and the worker identity to read and write document blobs. Each assignment uses a run-specific name and description so cleanup can verify ownership.

`document-events.bicep` uses the existing document account and running Functions app. It creates a Storage system topic and a BlobCreated/BlobDeleted subscription for the landing container. The destination is the `documentUploaded` Function discovered from the published app. Event Grid uses its system-assigned identity and a scoped Storage Blob Data Contributor assignment for the dead-letter container. The same compiled template has deployed successfully on Azure and GlobalStack. Runtime delivery and dead-letter behavior still require paired validation.

`document-diagnostic.bicep` is a separate component probe. It adds an owned
`event-diagnostics` container and a second BlobCreated subscription targeting
`documentEventDiagnostic`. The production subscription remains in place. Keeping
the diagnostic in its own module preserves the hashes of the already captured
document data and event templates. The diagnostic module passed a paired native
worker run on Azure and GlobalStack. Both targets wrote and read the marker;
the production handler still failed before the full document workflow.

`document-search.bicep` and `document-failures.bicep` add a Basic Search service and a Standard Service Bus failure queue with local-key authentication disabled. The Search module assigns schema administration and pilot query access to the publisher, document writes to the worker identity, and reads to the ingress identity. Its system-assigned identity receives Storage Blob Data Reader only on the existing `clean-projection` container. Pass the document storage account name and five role-assignment names to this module after deploying `document-data.bicep`. The queue module assigns send and receive rights to the worker identity. Both modules compile and deploy through the local ARM runtime in a synthetic test. The Search module has also deployed to Azure in the bounded paired pilot. Its public endpoint is a pilot configuration; the private-network requirements in the scenario specification remain unmet.

The local test uses reviewed compiled ARM fixtures in `compiled/` so CI does not depend on a private Bicep image. Source and fixture hashes are pinned in the test. Recompile and review both artifacts together whenever either Bicep module changes.

The push-index field definition in `document-app/search-schema.mjs` matches the committed outbox payload. The local Search query evaluator applies the application's tenant, clean-state, owner and group filter before returning hits. The endpoint-driven provisioner defines a separate JSON Blob index, managed-identity data source with a custom tombstone policy, explicit document-ID mapping, and five-minute indexer schedule. Deletion markers contain only the document ID and deletion flag, without extracted text. A bounded Azure/GlobalStack paired Search slice passed clean indexing, quarantine exclusion, soft deletion, and a wrong-container rejection. Later local production-path runs used the deployed scanner and worker to write clean and detected metadata, deliver the outbox to Search, and run the projection indexer. The local indexer currently reads Blob state inside the emulator process, so Search-to-Blob network behavior is not yet measured. The scheduled indexer is not a real-time path; push indexing carries the lower-latency requirement. Native Service Bus messaging, deployed ingress, private networking, and the complete combined Azure workflow remain outstanding.

`document-postgres.bicep` is a pilot template for an Entra-only Flexible Server, its administrator and the `documents` database. It follows the [server](https://learn.microsoft.com/en-us/azure/templates/microsoft.dbforpostgresql/2024-08-01/flexibleservers), [administrator](https://learn.microsoft.com/en-us/azure/templates/microsoft.dbforpostgresql/2024-08-01/flexibleservers/administrators) and [database](https://learn.microsoft.com/en-us/azure/templates/microsoft.dbforpostgresql/2024-08-01/flexibleservers/databases) resource definitions. The public network setting is provisional; it does not meet the scenario's private-network requirement. The [first provider validation](../evidence/document-postgres-validation-3ee3c25/) returned HTTP 200 on Azure and HTTP 501 on GlobalStack before the bounded local validator fix. Validation created no Azure resources. The later live deployment is recorded below; SQL initialization and worker access remain untested.

`document-postgres-paired.mjs` is a separate live deployment probe for this same compiled template. It reserves a USD 12 allowance inside the authorized experiment ceiling, uses the authorized pilot group, starts a detached cleanup watchdog before provisioning, submits the unchanged template to Azure first, replays it locally, and removes only the tagged server and its deployment record after the attempt. `document-postgres-cleanup.mjs` refuses to delete a server with foreign run tags and preserves the pilot group. The runner records creation and cleanup only; SQL and application behavior remain separate gates.

`document-postgres-sql-paired.mjs` reuses the frozen deployment template and adds a temporary single-address firewall rule on each target for test access. It attempts Entra-authenticated PostgreSQL access and the document schema on Azure. The local in-memory ARM replay has no PostgreSQL wire-protocol endpoint, so the runner records local SQL as untested rather than claiming parity. The watchdog deletes the firewall rule before the server, and independent Azure inventory must be empty before the run allocation is closed. The temporary public rule is a pilot access mechanism, not evidence that the private-network requirement is met.
The runner exits unsuccessfully when the local firewall or SQL path is incomplete, even if the Azure-only SQL probe passes. It records each SQL connection attempt for later runs.

The [completed SQL pilot](../evidence/document-postgres-sql-paired-20261109/) found successful ARM deployments on both targets and successful Azure Entra SQL login and schema creation. The same temporary firewall-rule PUT returned 501 on GlobalStack. Local SQL and worker/ingress identities remain open.

`document-postgres-roles.bicep` extends the isolated PostgreSQL pilot with tagged worker and ingress user-assigned identities. `document-postgres-roles-paired.mjs` runs an Azure-first comparison that creates those identities, uses their principal IDs to bootstrap nonadmin Entra database roles, verifies the intended SQL grants, and cleans up the server, firewall rule, identities and deployment record. The local fixture test verifies that the compiled template creates both identities without claiming a SQL data-plane result. This pilot does not replace the unchanged document application stack or its private-network requirement.
The [completed role pilot](../evidence/document-postgres-roles-paired-20261109/) proved Azure role creation and grant readback, including ingress denial on the outbox. GlobalStack accepted the ARM identity and database resources but still returned 501 for the firewall rule; local SQL remains untested.

The [first paid pair](../evidence/document-postgres-paired-efb90ad/) reached Azure deployment success but GlobalStack rejected the Entra-only server because it still required a password administrator. The Azure server and deployment record were deleted; a stale child inventory read caused first-pass cleanup to report incomplete. A later recovery verified zero resources and marked the allocation cleanup-verified. The local creation validator now accepts this captured Entra-only shape, and the cleanup helper waits for inventory convergence. A [local replay](../evidence/document-postgres-local-replay-f10ee8a/) of the original Azure request then returned HTTP 201 and `Succeeded` with all three resources readable. It did not make another paid Azure deployment or test SQL behavior.

Deploy the data module before the worker app so its Blob endpoint is available in the worker's initial settings. Deploy the event subscription only after the Functions host reports the Event Grid trigger. Compile one immutable revision and run Azure first, then replay it unchanged locally. Record any provider errors and clean up each run. Do not add the new services to a paid run until the ownership-checked cleanup and watchdog cover their resource IDs and deployments.

`worker-scanner-paired.mjs` extends the worker/scanner component run with the document and diagnostic modules. It reserves a USD 12 experiment envelope, starts a detached ownership-checked cleanup watchdog, deploys to Azure first, then replays each template locally. It records a failed stage as a failed stage, including an Azure/GlobalStack mismatch. All owned document resources and deployments must be absent before the budget reservation can be marked cleanup-verified. The opt-in upload and event diagnostics test a managed-identity Blob write and a correlated event marker, but do not substitute for document ingestion and search.

For long runs, invoke `paired-detached.mjs` with the same environment as the runner. It starts the runner in a separate process group and writes `launch.json` and `launcher.log` in the private run directory. Poll the run's `result.json` and watchdog result; a launch record alone is not a completed test. Reconcile any interrupted budget allocation only after a fresh Azure inventory and deployment absence check.

If both the runner and watchdog stop, use `document-paired-recover.mjs` with the
absolute private `private-cleanup.json` path and a new private result path. The
recovery command refuses a live runner, verifies ownership, finishes any
remaining cleanup, independently checks that Azure has zero resources and
deployment records in the preserved pilot group, then marks the allocation
cleanup-verified. It does not recover local container state or measured Azure
billing; verify those separately. The certificate-backed Azure CLI session must
be available through `PAIRED_AZURE_CERTIFICATE_FILE`.

The Event Grid identity and dead-letter role follow [Microsoft's managed-identity guidance](https://learn.microsoft.com/en-us/azure/event-grid/managed-service-identity). The subscription shape follows the [system-topic Bicep reference](https://learn.microsoft.com/en-us/azure/templates/microsoft.eventgrid/systemtopics/eventsubscriptions).
